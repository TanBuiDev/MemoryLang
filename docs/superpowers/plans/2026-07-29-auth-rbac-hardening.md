# MemoryLang Authentication and RBAC Hardening Implementation Plan

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the coarse `profiles.is_admin` authorization model with database-backed least-privilege RBAC, protect administrative operations with MFA and short-lived admin sessions, and eliminate browser exposure of AI secrets.

**Architecture:** Keep Supabase Auth and Google OAuth for identity. Put role assignments and permissions in a private `security` schema, enforce them through PostgreSQL RLS/RPCs, and send sensitive mutations through authenticated Edge Functions that validate AAL2, an active admin session, permission, payload, and audit record in one server-controlled flow. The frontend only uses permission information for UX.

**Tech Stack:** Supabase Auth/MFA, PostgreSQL 17 + RLS, Supabase Edge Functions (Deno), React 19/TypeScript, Zod, Vitest, Supabase SQL tests.

---

## Confirmed findings and scope

- `supabase/config.toml` now enables local TOTP enrollment and verification. This is only a local development setting.
- `parse-exam-vision` currently accepts unauthenticated requests, uses the service-role client, accepts `customApiKey`, retains a `VITE_GEMINI_API_KEY` fallback, and can consume vault keys. Treat this as a production hotfix.
- `get_key_pool_secret_for_test` returns `encrypted_value` to the React client. Remove it instead of further restricting the UI.
- `profiles.is_admin` is currently used by `AdminRoute`, direct client mutations, RLS, and secret-vault RPCs. Preserve it only as a compatibility bridge while each protected operation moves to a named permission.
- There is no current `aal2`, `admin_sessions`, or server-side immutable audit implementation.
- Do not claim production RLS coverage until the SQL tests run against a local seeded database and a staging/production verification has been performed.

## Acceptance criteria

- No browser bundle, REST RPC, or React state contains a raw provider/API key.
- Unauthenticated or unauthorized callers cannot invoke AI import or any sensitive admin mutation.
- A user cannot read or write another user's learning data through UI, REST, RPC, Storage, or Edge Function.
- `exam_admin` cannot assign roles; `security_admin` cannot modify exams; `support_admin` cannot read private learning content by default.
- AAL1 admins are denied sensitive operations; AAL2 plus a valid non-revoked admin session is required.
- Role revocation invalidates all admin sessions and takes effect on the next authorization check.
- Every role and sensitive mutation produces a non-forgeable server-side audit event with a reason and request correlation ID.
- Tests cover both allow and deny paths for each policy and function before production rollout.
